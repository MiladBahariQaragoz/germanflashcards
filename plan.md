# High-Level Plan: German Flashcards Bot V2

> **Status: ✅ FULLY IMPLEMENTED** (2026-05-25)

## 1. Database Restructuring & Multi-User Support ✅
Right now, the system assumes a single user and stores study progress directly on the flashcard document. We need to split this up:
- **`cards` Collection**: Keep the global vocabulary (words, translations, sentences, CEFR levels) completely separate from study progress. These are read-only reference documents populated by the migration script.
- **`users` Collection**: Store registered user profiles — their Telegram chat ID, registration date, and preferences (study direction: DE->EN or EN->DE, preferred CEFR levels).
- **`user_progress` Collection**: Store the FSRS algorithm data (due date, state, stability, difficulty, step) for each user-card combination. One document per (user_id, card_id) pair.
- **`otps` Collection**: Store one-time passwords generated by the admin, their usage status, and expiration timestamp.

## 2. Migration Plan ✅
The existing `flashcards` collection has V1 data with FSRS progress embedded directly on each card. We need a migration script (`scripts/migrate_v2.py`) that does the following:

**Step 1 — Populate `cards` collection from JSON files:**
- Read all four JSON files from the project root: `combined_words_a1.json`, `combined_words_a2.json`, `combined_words_b1.json`, `combined_words_b2.json`.
- Each JSON file is a list of objects with fields: `word`, `translation`, `german_sentence`, `english_translation`, `cefr_level`.
- Insert all records into the `cards` collection as clean vocabulary documents (no FSRS fields).
- Create a unique index on `word` to prevent duplicates on re-runs.

**Step 2 — Migrate existing V1 FSRS progress to `user_progress`:**
- Read all documents from the old `flashcards` collection.
- For each document that has non-default FSRS data (i.e., `fsrs_state != "New"` or has been reviewed), look up the matching card in the new `cards` collection by `word`.
- Create a `user_progress` document for the admin user (hardcoded `AUTHORIZED_CHAT_ID`) linking that card's `_id` with the existing FSRS fields.
- Cards that are still in the default "New" state with no review history can be skipped — they'll be picked up naturally from the `cards` collection.

**Step 3 — Index creation:**
- `user_progress`: compound index on `(user_id, due_date, fsrs_state)` for efficient session queries.
- `cards`: index on `cefr_level` for filtering by level.
- `otps`: index on `code` for fast lookup during login.

> ⚠️ **Migration not yet run on VM.** See SESSION_LOG.md for deployment steps.

## 3. Authentication & Authorization Flow ✅
- **Admin**: Remains the hardcoded `AUTHORIZED_CHAT_ID` from the environment variable. The admin has access to extra commands and is never required to go through OTP registration.
- **Admin Command `/create_invite`**: Generates a random OTP, saves it to the `otps` collection with a `used: false` flag and an expiration timestamp (48 hours), and sends it back to the admin in chat.
- **User Onboarding**: When an unregistered user messages the bot, they are prompted to register via `/login <password>`.
- **Validation**: If the password matches an unused, non-expired OTP, the bot registers their chat ID in the `users` collection and marks the OTP as `used: true`. From that point on, authorization is a database check against `users` rather than a hardcoded ID check.

## 4. Queue Management Updates ✅
- The current `SessionQueue` acts as a singleton for one user. Refactor `queue_manager.py` to hold a dictionary of queues keyed by `user_id` (e.g., `queues[user_id]`), so multiple users can study simultaneously without interference.
- The `kill_switch` must also become per-user — stored as a field on each queue entry (e.g., `queues[user_id].kill_switch`), not as a global boolean. It gets set to `True` when that specific user finishes their session, and reset to `False` on the morning trigger for that user.
- The morning scheduler and nag checks will iterate through all registered users, checking their specific `user_progress` due counts and sending customized reminders. A user with an active `kill_switch` is skipped by the nag check until the next morning reset.

## 5. User Preferences & Settings Menu ✅
- **Settings Interface**: Add a `/settings` command that opens an inline keyboard menu.
- **Study Direction**: Allow toggling between DE->EN or EN->DE. Stored in the `users` document. Read dynamically when sending the front of a card during a session.
- **CEFR Level Selection**: Allow users to select which CEFR level(s) they want to draw new cards from (A1, A2, B1, B2). Stored as a list in the `users` document. The database queries for new cards will filter by the user's selected levels.
